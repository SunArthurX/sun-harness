Execution targets and job recovery

The desktop can review a job for a saved gateway while staying on its local execution host. The target ID comes from the gateway installation. The session on that target supplies the workspace and sandbox.

What happens when the launch reply disappears?

The controller saves an operation before dispatch. The provider saves its job reservation before spawning a process. Reconnecting queries that same operation and updates the original row.

flowchart TD
  A[Review the target and command] --> B[Commit controller operation]
  B --> C[Verify target identity]
  C --> D[Reserve provider job ID]
  D --> E[Launch detached process]
  E -->|Receipt received| F[Record provider state]
  E -->|Reply missing| G[Show reconciling]
  G --> H[Query the original operation]
  H -->|Matching receipt| F
  H -->|No verified receipt| G

How can a Docker job stop independently?

The job starts in a container with the operation ID in its labels. The provider saves the cancellation request, checks the container identity, and removes that container. The cancellation acknowledgement and process outcome are separate fields.

flowchart TD
  I[User requests cancellation] --> J[Persist request]
  J --> K[Verify process or container identity]
  K -->|Reachable and verified| L[Deliver cancellation]
  L --> M[Persist acknowledgement]
  M --> N[Observe process outcome]
  K -->|Unavailable| O[Keep pending]
