09 · Background jobs

The loop in page 02 is synchronous: call a tool, wait, continue. That is wrong for a ten-minute test suite or a dev server. This iteration splits invoked from finished, so the result can re-enter the session later, as a logged event.

The finding and the principle

Claude Code 2.1.319 moves long-running MCP tool calls to the background right away and tells the model the result when it is done. The intel report named the mechanism: async tool results as eventual delivery. It works because the loop is already event-driven: a completion is just another input.

Design questions

Why deliver the result as a user message instead of rewriting the old tool result?

The log is append-only, and the model already saw the "moved to background" result. Rewriting it would make the transcript disagree with what the model actually saw, which breaks model-visible means logged. A new user/message with source: job is honest about time: the result arrived later.

What if the agent is in the middle of a run when the job ends?

The delivery goes through the same queue as user follow-ups and arrives when the run ends. The queue had to learn to keep each message's source: in the first version a queued job result was replayed as a user message.

Do jobs survive a restart?

Not yet. Child processes die with the app, so on start-up any job without a job/finished event is marked lost and the session shows it. A long-lived owner process (the gateway, page 10) is the place to make jobs outlive a window.

Why doesn't Stop on a session kill its jobs?

Jobs are often things you want to keep, such as a dev server you are clicking through. Stopping the agent's thinking and stopping its processes are separate decisions, so jobs have their own Stop button and the job_kill tool.

If the loop is a pure function of the log, asynchrony is cheap: anything that finishes later becomes one more event, and the loop takes it from there.
