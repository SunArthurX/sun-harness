03 · Extensions & knowledge

Every extension feeds one of two parts of the harness: context (what the model knows) or tools (what it can do). Seeing them this way keeps five extension systems from turning into five architectures.

Rules, loaded from general to specific

flowchart TB G[~/.sun/AGENTS.md — global] --> R1[repo-root AGENTS.md] R1 --> R2[sub/dir AGENTS.md or CLAUDE.md] R2 --> SR[.sun/rules/*.md] SR --> CR[.cursor/rules alwaysApply] CR --> IDX[specs/*.md titles — source of truth]

Rules are re-read before every model request, so an edit to AGENTS.md applies to the very next step of a running session. Symlinked files such as CLAUDE.md → AGENTS.md are de-duplicated by real path.

Skills: progressive disclosure

sequenceDiagram participant P as System prompt participant M as Model participant T as load_skill P->>M: "- deploy: How to deploy" (one line per skill) M->>T: load_skill("deploy") T-->>M: SKILL.md body + list of bundled files M->>M: follows the steps, reads bundled files if needed

Why not put every skill in the prompt?

This machine already has 17 skills in ~/.claude/skills, and some descriptions are hundreds of words. Bodies would cost thousands of tokens on every request. The index costs one line each, and only the skill actually used gets loaded. Because the format matches Claude Code's, those 17 skills worked in sun-harness without changes.

MCP, plugins, hooks

  • MCP uses the official TypeScript SDK (stdio, streamable HTTP, SSE). Tools are namespaced mcp__server__tool and default to risk exec, so they ask in auto-edit mode unless the server is marked trust. The test suite spawns a real stdio MCP server fixture.
  • Plugins are ESM folders in ~/.sun/plugins. One small API registers tools, modes, knowledge providers, prompt sections and event listeners. A broken plugin reports status: error and never takes the host down.
  • Hooks are shell commands with Claude-Code-like semantics: event JSON on stdin; exit 2 blocks; stdout becomes context. A stop hook can send the agent back to work, for example "tests fail", at most three times per run.

Knowledge without embeddings (yet)

The personal knowledge base is any folder of Markdown. It is chunked by heading and ranked with BM25:

score(q, d) = Σ  idf(t) · f(t,d)·(k1+1) / ( f(t,d) + k1·(1 − b + b·|d|/avgdl) )      k1 = 1.4, b = 0.75
             t∈q

BM25 needs words. How does it search Chinese, which has no spaces?

With character bigrams. 知识库 ("knowledge base") becomes 知识, 识库. Bigrams match most Chinese words without a dictionary-based segmenter, and English words are tokenized normally in the same pass. A test checks that a recipe note containing 红烧肉 (braised pork) is found by that query.

Why not a vector database?

BM25 is deterministic, offline, instant to index, and needs no embedding model or API key. The KnowledgeProvider seam means embeddings can arrive later as just another provider. The company knowledge base is reserved the same way: an HTTP contract (POST /search) that any internal search can implement.

Modes are prompts plus tool filters

ModeInspired byWhat changes
codingClaude Code, Codexspec-first, minimal edits, verify
agentManusplan with todos, research the web, delegate with task, deliver files
assistantHermes, WorkBuddymemory-first, KB lookups, reminders; no shell or edit tools

Subagents are just child sessions: same log format, same loop, with a parent field. Their approvals are shown in the parent session, so the human sees them where they are looking.

Classify each extension as context or tools before designing it. Context is assembled into the prompt; tools register in one registry under one policy. New extension types then fit without new architecture.
