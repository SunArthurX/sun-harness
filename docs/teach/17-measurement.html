17 · Measure first

Coding success is a product of four probabilities: understanding × plan × execution × verification. You cannot improve a product you never measure. Phase 0 builds the instrument before turning any knobs.

The strong model passes nearly everything. Is the suite useless?

For pass rate on that model, yes: a benchmark at its ceiling cannot show improvements. Twelve hard tasks were added and the strong model still passed them. Two signals remain. First, cost: about 60k input tokens per task, with 1.8 M vs 2.6 M between two identical runs, which also shows how noisy one run is. Second, a weaker model, where the harness has to compensate. On qwen-flash the suite drops to 55.6% and the failure modes become visible.

What the weak model revealed

Where do the failures come from?

Classifying every failing tool call in the logs gave three causes. 93 were edit_file: old_string not found, with sessions burning all 60 steps re-trying edits from memory. 38 were web_search: fetch failed: the search backend is unreachable on this network, but the tool was still offered and the model kept calling it. One was the worst kind: the model produced malformed JSON for tool arguments, the log kept it, and the provider then rejected every later request with HTTP 400, so the session was dead.

These three findings define the first Phase 1 work: tolerant edits with read-before-edit, capability gating for tools, and never sending malformed tool calls back to a provider.

Build the measuring stick, then test the measuring stick. An eval with an impossible task or an unfair check produces confident wrong conclusions.
