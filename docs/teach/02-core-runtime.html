02 · The core runtime

The core is small: a log, a loop that reads the log, providers that speak two wire formats, and an error taxonomy that decides whether to retry, fall back, or pause.

The log is the state

Every session is one JSONL file. Each line is an event with a sequence number. The loop never keeps state between steps; it re-derives everything from the log. This one decision gives resume, crash recovery, model switching, auditing and reflection for free.

{"seq":1,"type":"user/message","text":"Create fib.py ..."}
{"seq":3,"type":"request/header","model":"deepseek/deepseek-chat","systemPrompt":"...","tools":["read_file",...]}
{"seq":4,"type":"assistant/message","text":"","toolCalls":[{"id":"call_0","name":"write_file","arguments":"{...}"}]}
{"seq":5,"type":"tool/result","callId":"call_0","name":"write_file","output":"Created fib.py (18 lines)","isError":false}
{"seq":9,"type":"run/status","status":"paused","reason":"quota","detail":"HTTP 402: Insufficient Balance"}

Model-visible means logged (borrowed from DeepSeek Harness): the system prompt is logged as request/header whenever it changes, so any request can be reconstructed exactly.

The loop

sequenceDiagram participant H as HarnessHost participant A as Agent.run() participant L as Session log participant M as Model participant T as Tools H->>L: append user/message H->>A: run(signal) loop until nothing is owed A->>L: pendingToolCalls()? alt calls pending A->>T: policy check, hooks, execute T-->>L: tool/result end A->>L: owesRequest()? (last event is user input or tool result) A->>M: system prompt + deriveMessages(log) + tool schemas M-->>A: streamed text, reasoning, tool calls A->>L: assistant/message end A->>L: run/status idle

Two details that matter in practice:

  • Pairing. Providers reject an assistant tool call without a matching result. deriveMessages() inserts a synthetic "interrupted" result for any call that was never answered, such as after a crash.
  • Owed request. "Should I call the model?" has one answer: yes if the latest conversational event is user input or a tool result. That single rule makes run() and resume() the same function.

Errors decide the next move

stateDiagram-v2 [*] --> Running Running --> Retrying: rate_limit / network Retrying --> Running: backoff 1s,2s,4s… (≤5) Retrying --> Paused: retries exhausted Running --> Fallback: quota / auth Fallback --> Running: next fallbackModels entry Fallback --> Paused: no fallback left Running --> Compacting: context_length Compacting --> Running: retry once Running --> Idle: nothing owed Paused --> Running: resume (same model or switched) Running --> Aborted: user stop

How do you tell "quota exhausted" from "rate limited"? Both are often HTTP 429.

By the body. 402 is always quota (DeepSeek "Insufficient Balance"). A 429/403/400 whose body mentions balance, quota, billing or credits, including Chinese wording such as 余额 (balance), 额度 (credit limit) or 配额 (quota), is treated as quota. Any other 429 is a rate limit. Tests cover DeepSeek's 402 and GLM's 1113 余额不足 ("insufficient balance") 429 against a local SSE server.

What exactly happens when quota runs out mid-task?

The model request fails, nothing is appended except run/status paused (quota), and the run returns. Later, resume(id) or resume(id, {model}) re-derives the same history and sends the same request, on the same or another model. This was verified live: a session on an invalid key paused with auth, then sun resume <id> --model deepseek/deepseek-chat logged a model/switch and finished, sending the original user message exactly once.

Compaction at clean boundaries

Long runs outgrow the context window. Compaction summarizes older history into a context/compaction event, but only up to a clean boundary: a point with no outstanding tool calls. Cutting between a call and its result would break pairing.

Bugs found by tests

A run that finished on its last allowed step reported "paused: max_steps". Why?

The loop exited because of the step counter before checking whether anything was still owed. Fix: after the loop, return idle when nothing is pending. The test was tightened to count exact model requests, so the fix is pinned.

Make the durable log the only state and make every decision a pure function of it. Resume, crash recovery and quota handling then stop being features you build and become properties you test.
