Settings transactions

Settings used to return the whole configuration and overwrite it without checking the revision. The settings service now exposes a field allowlist and serializes writes across processes.

flowchart LR
  A[Desktop, web or CLI] --> B[Redacted snapshot and revision]
  B --> C[Scoped edit with expected revision]
  C --> D{Lock and compare}
  D -->|Stale| E[Reload and review pending edit]
  D -->|Current| F[Validate and prepare audit]
  F --> G[Flush and replace config]
  G --> H[Record outcome and apply at safe boundary]

Why separate the file from the settings view?

The runtime still needs credential values and extension data. The renderer gets a DTO constructed from explicit fields. Old gateway method names return a protocol mismatch.

What happens if a process dies?

Write the full replacement privately, flush it, then rename it. The old or new JSON survives depending on the crash point. Recovery can remove a dead process's unique lock marker. The prepare record remains available when a crash interrupts the audit outcome.

How is the behavior checked?

The offline suite races real processes and injects write failures. The desktop smoke test uses a temporary data directory and exercises stale-state recovery through Electron, then connects the same renderer to the gateway over HTTP.
