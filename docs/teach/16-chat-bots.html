16 · Chat bots

An assistant you can only reach at your desk is half an assistant. Hermes treats chat apps as one more surface of the gateway. sun-harness does the same: one platform-neutral bridge, and thin adapters for Telegram, DingTalk and plain webhooks.

Design questions

Who can talk to the bot?

Only allowlisted platform user ids, and an empty list means nobody. A stranger gets one reply containing their own id (so the owner can add them) and nothing else: no session is created and no model is called.

How do approvals work in a chat?

The bot posts "⚠️ Approval needed" and waits for /approve, /approve always or /deny, answered with the current prompt id (page 14). There was a trap here. Registering the bot as an approver the old way, globally, would have made every session's approvals wait, including CLI runs nobody was watching, which breaks the fail-closed rule from page 06. Approvers are now scoped: the bot can only approve its own chats' sessions, and everything else is still denied when no human is present. A test pins exactly this.

Why long polling for Telegram but callbacks for DingTalk?

Each uses what needs the least infrastructure. Telegram's getUpdates works from behind NAT with no public URL. DingTalk's outgoing robot only pushes to a URL, so the gateway exposes /bots/dingtalk, verifies DingTalk's HMAC signature and timestamp, and replies through the per-message sessionWebhook.

How can a script use it synchronously?

POST /bots/webhook?wait=1 holds the response until the run ends, or until it stops on an approval, and returns {sessionId, replies}. That makes the bot a one-line curl API for shortcuts, cron jobs and other agents.

What was verified?

Telegram against a local fake of the Bot API (allowlist, an approval answered in the chat, replies); DingTalk signature rejection and acceptance with replies to a fake session webhook; and live, the webhook bot on a real gateway with DeepSeek: a stranger refused, a question answered, a shell command held for approval, then /approve ran it and the output came back. The real Telegram API is unreachable from this network, so live Telegram is left to the owner's token.

Put the policy in the bridge, not the adapters. Allowlists, sessions and approvals are written once; a new platform is a hundred lines of translation.
