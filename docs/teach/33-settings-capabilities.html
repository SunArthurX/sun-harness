Capability discovery and dispatch

Settings clients need to know what the current host and surface can do. A versioned settings snapshot now includes stable capability IDs, current state, and reason codes. The same method table shapes the Electron and gateway responses.

flowchart LR
  C[Client settings protocol] --> P{Version matches}
  P -->|No| E[Protocol error]
  P -->|Yes| S[Settings snapshot]
  R[Runtime and extension registry] --> S
  A[Native adapter] --> S
  D[Desktop native invocation] --> N{Adapter still available}
  N -->|Yes| A
  N -->|No| U[Explicit capability error]
  W[Gateway native invocation] --> H[Unknown route]

Why check again at dispatch?

A capability can change while a client has an old snapshot or a tool call waits for approval. Reload removes old plugin registrations. The tool wrapper verifies that its original registration is still active before executing. It does not reuse an approval for a newly loaded tool with the same name.

How do failed plugins stay isolated?

The loader stages registrations during activation. Only successful activation publishes them. The capability descriptor includes a diagnostic code while the extension manager retains its existing local diagnostic text.
