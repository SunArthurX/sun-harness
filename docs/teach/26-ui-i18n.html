26 · Pages in English and Simplified Chinese

The desktop and the gateway web UI are the same React renderer. They now switch between English and Simplified Chinese. The rule that makes it last: a new screen is not done until both languages are in the same change, and a test fails if they are not.

English as the key, Chinese as the dictionary

Message ids (nav.sessions) need a parallel English file and drift when the copy changes. Two full locale files duplicate every sentence. The cheap durable option is gettext-style: the English sentence is the key. t('Open') is Open in English and the value from locale-zh-CN.ts in Simplified Chinese. A missing translation falls back to English instead of showing nav.open.

flowchart LR JSX["JSX: t('Open')"] --> T[t] T -->|en| EN[Open] T -->|zh-CN| ZH["locale-zh-CN: 打开"] SCAN["i18n.mjs scanner"] --> JSX SCAN --> KEYS[English keys] KEYS --> TEST[i18n.test.ts] ZH --> TEST

Why not localize the CLI too?

Scripts and bots parse CLI output. Mixing translated status lines with flags would break that. The pages are for humans; sun stays English, matching specs and docs.

How does “system” pick a language?

resolveLang reads navigator.language. Any locale starting with zh becomes Simplified Chinese; everything else becomes English. Settings can lock en or zh-CN. The choice is ui.language in ~/.sun/config.json, applied in main.tsx before the first React render so the welcome screen is already in the right language.

A test that outlives the checklist

Wrapping strings by hand is easy to skip on the next feature. The scanner walks the renderer AST: JSX text, placeholder / title / aria-label, object fields like label and hint, and confirm / alert. Anything with words that is not inside t() or tk() is a violation. A second check requires every collected key to exist in zhCN with the same {name} placeholders, and to contain Chinese characters unless it is a product name or URL.

What about t(status) where the English is a runtime enum?

The scanner only sees string literals. Session status, tool risk, file change, job state, skill scope and similar values are listed as tk('idle'), tk('running'), … in i18n.ts so they are keys like any other. Context-report suggestions from core are registered the same way in Context.tsx.

A language switch left the sidebar in English. Why?

groupSessions was memoized on the session list only. The labels Pinned / Today were captured in the old language. Adding lang to that memo (and remounting the main pane with key={lang}) makes the whole shell follow the setting.

Where the human switches

Settings has System / English / 简体中文. The left rail has an EN / 中 button at the bottom so the switch is one click from any page. Both write ui.language and call setLang.

Lessons

  • If the English sentence is the key, a copy change is one edit plus one dictionary line, not a hunt for an id.
  • “Support Chinese” without a failing test lasts until the next page. The scanner is the policy.
  • Memoized labels must list the current language as a dependency, or a switch looks like a no-op.
