Iteration 8 · spec specs/015-durable-jobs.md

13 · Jobs that survive

Page 09 made long commands asynchronous, but they still died with the process that started them. With a gateway that restarts on upgrades and crashes, "durable before clever" has to cover jobs too.

Move the job's state out of memory

A job used to be a child process whose output came through pipes and whose exit was an in-memory event. Both disappear when the parent dies. The fix moves all three onto disk:

bash -c "$SUN_JOB_CMD" >>"$SUN_JOB_LOG" 2>&1; echo $? >"$SUN_JOB_EXIT.tmp" && mv "$SUN_JOB_EXIT.tmp" "$SUN_JOB_EXIT"
  • Output goes straight to <id>.log from the shell, with no pipe to a parent.
  • Exit status is written by the wrapper itself, atomically (temp file and rename), so a half-written file can't be misread.
  • Identity lives in <id>.json: session, command, pid, file paths.
  • The wrapper runs detached in its own process group, so it is not killed with the parent, and job_kill can stop the whole group.

pid + marker in command line} A -->|yes| W[watch every 500 ms, deliver at the end] A -->|no| L[lost → deliver, agent can restart it]

Design questions

Why check the process's command line, not just whether the pid exists?

Pids are reused. After a reboot, pid 75128 may be some unrelated program, and kill(pid, 0) would report it alive forever. The wrapper's command line contains the literal marker SUN_JOB_EXIT, so the job is only considered alive if ps shows our wrapper.

Why restore after cleaning up interrupted sessions, not before?

Restoring can deliver a finished job immediately, and delivery starts a run, which sets the session to running. The cleanup step marks sessions that are running at start-up as "interrupted". In the other order, a freshly started, healthy run would be labelled interrupted. The order is part of the design and is commented in init().

How was it verified?

Unit tests restart hosts mid-job (delivered by the second host), after a job finished with no host running (delivered on start), after the wrapper was killed from outside (lost), and with killOnExit. Live: through the real launchd gateway, a job ran sleep 12, the gateway was kill -9'd, launchd started a new one, it re-attached, saw exit 0, and the agent reported the output.

If something must outlive a process, its state can't live in that process. Put output, identity and completion on disk, and any successor can pick the work up.
