Settings compatibility fixtures

Settings persistence must preserve existing user data. The first implementation task records how the current runtime reads legacy configuration, supplies defaults and replays attachments.

How are the checks isolated?

Each test creates a temporary SUN_HOME and removes it afterward. The provider fixture uses an invalid domain and synthetic credential values. The tests exercise the configuration and replay paths directly.

flowchart LR
  A[Temporary SUN_HOME] --> B[Legacy configuration]
  A --> C[Session and owned image]
  B --> D[Load and save compatibility]
  C --> E[Replay after reopen]
  E --> F[Delete fixture and verify missing attachment state]
  G[Fake window adapter] --> H[Available, denied and cancelled states]

What happens when a dependency finishes?

Mutation tests start from a synthetic planned state. This keeps their negative cases valid as the actual manifest accumulates completed tasks and evidence.
