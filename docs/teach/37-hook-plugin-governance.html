Hook trust and plugin lifecycle

The work began with static hook discovery and digest-based review. The fixture runner then reused the runtime sandbox and bounded process runner. The renderer exposes the same review and fixture operations as the CLI. Plugins gained static manifests and a host-owned lifecycle for their registrations.

flowchart TD
  A[Hook source] --> B[Validate event, matcher and command]
  B --> C[Compare reviewed digest]
  C -->|Current| D[Run in bounded sandbox]
  C -->|Missing or stale| E[Skip or block by hook policy]
  D --> F[Persist outcome and model-visible feedback]
  G[Plugin manifest] --> H[Inspect requested actions]
  H --> I[Activate and publish a registration generation]
  I --> J[Commit disabled setting at current revision]
  J --> K[Revoke this generation]
  K --> L[Reject new and queued calls]
  K --> M[Drain started calls]
  M --> N[Audit settlement and publish disabled state]

What invalidates hook review?

Trust is tied to the reviewed identity, canonical source path and exact source bytes. A change after preview requires another review. Matching policy hooks with a block policy fail closed. Timeout and cancellation terminate the hook process tree, and output has a fixed byte budget.

What happens to an approved call when the plugin is disabled?

An approval can arrive after the registration was revoked. The tool wrapper checks its own generation at dispatch. A re-enable can publish a new generation, and the old wrapper still fails. Work that entered before revocation releases its in-flight count when it settles.

What do requested actions tell the user?

A fixed vocabulary describes the author's declaration before any plugin code runs. Registration names show the contributions of the current generation. Enabled local JavaScript has host process privileges.
