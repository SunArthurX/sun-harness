18 · Make the mechanics reliable

The weak model in phase 0 did not fail because it could not reason. It failed because edits did not apply, tools that could not work were offered, and one malformed tool call killed a session. Phase 1 fixes the mechanics in the harness, measures every change, and keeps or reverts it by the numbers.

Where a coding run loses

flowchart LR U[understand the repo] --> P[plan] --> E[edit] --> V[verify] --> D[declare done] U -.->|repo map, plan mode| U E -.->|tolerant replace, apply_patch, stale check, diagnostics| E V -.->|done gate| V D -.->|checkpoints + undo, best-of-N| D

Success is roughly the product of the stages. A 70% chance that an edit lands, repeated over five edits, already gives 17%. Tolerant edits attack the largest factor first, because the baseline logged 93 failures of exactly one message: old_string not found.

1 · Edits that land

flowchart TD A[edit_file old → new] --> X{exact match?} X -->|once| W[write] X -->|no| C{after CRLF normalization?} C -->|once| W C -->|no| S{whitespace-insensitive line match?} S -->|once| R[re-indent replacement to the file] --> W S -->|several| AMB[refuse: ambiguous, add context] S -->|none| CL[refuse + closest region with line numbers] W --> CP[checkpoint before write] --> DG[syntax check → warning in result]

Isn't whitespace-insensitive matching dangerous?

Only if it can match the wrong place. The match is accepted only when it is unique; otherwise the tool refuses and asks for more context. The replacement is re-indented to the indentation the file actually uses, which is what the model meant.

Why a second edit tool (apply_patch)?

Multi-file changes done as N separate edits can fail halfway and leave a broken tree. The Codex-style patch is validated completely before anything is written: all files or none. Hunks use context lines with the same tolerance, plus optional @@ anchors.

Read before overwrite, fresh before edit — and an eval-driven correction

The first version required read_file before any edit. On qwen-flash it helped: blind overwrites disappeared. On deepseek-chat it hurt: the edit failure rate went from 0% to 20% (14 refusals in 36 tasks), because strong models often look at files through grep or cat and then edit correctly. None of the refusals prevented a wrong edit.

The rule was narrowed: whole-file overwrites still require a read; anchored edits do not (their old text must match anyway). The staleness check stayed for all three: if a file changed on disk since the agent last saw it, the edit is refused.

Loop breakers

The all-phases qwen-flash run showed the edit failure rate back at 38.9%. Classifying the failures: 100 of 102 failing edit_file calls were on files the model had read, and 147 failures came from just two sessions. The model wrote old_string as the code it wanted to see, not the code in the file, and re-sent the identical call up to 30 times while the error showed the right lines. Two breakers: from the second miss on a file the error includes the whole current file with line numbers and suggests write_file; and any repeated byte-identical failing call is flagged with its count and told to change approach. DeepSeek showed a third loop: nine refused overwrites of an unread file, each with different content, so the identical-call check never fired. A refusal now hands over the file's current content and counts it as read: the next overwrite is informed, and the guarantee (no write without seeing the file) still holds.

3 · The done gate

sequenceDiagram participant M as Model participant H as Harness participant P as Project checks M->>H: final answer (after editing) H->>P: verify commands (.sun/project.json or detected) alt pass P-->>H: exit 0 H-->>M: verify/result passed, run ends else fail (attempt ≤ 2) P-->>H: output H->>M: user/message source=verify: "fix the cause, do not weaken tests" M->>H: more edits … end

The model's "done" becomes a claim the harness checks. Commands come from .sun/project.json or are detected (package scripts, tsc --noEmit, node --test, pytest/unittest, cargo, go). The gate only runs when files changed since the last verification, so chat turns cost nothing.

4 · Context: cache, map, plan

How do you get prompt-cache hits without making the prompt worse?

Keep the prefix stable. Messages are append-only already; the repository map is computed once per session; recalled memories (phase 5) are appended as messages instead of changing the system prompt. Then report what the provider says: DeepSeek prompt_cache_hit_tokens, OpenAI/DashScope prompt_tokens_details.cached_tokens, Anthropic cache_read_input_tokens.

DashScope reported 0 cached tokens. Is caching broken?

Two identical 3.9k-token requests both returned cached_tokens: 0: implicit caching did not engage. With explicit cache_control markers on content blocks (supported by DashScope's OpenAI-compatible API), the second request read 3,911 of 3,922 tokens from cache. The provider option cacheControl marks the system prompt and the newest message; the DashScope preset turns it on.

Repository map: definitions per file (functions, classes, types, methods for JS/TS, Python, Go, Rust, Java), files ranked by how often other files reference their names (a cheap stand-in for PageRank on the reference graph), rendered within 6,000 characters. The repo_map tool gives a fresh, filtered view.

Plan mode: read-only tools plus exit_plan_mode, which has exec risk so it passes approval: the human reviews the plan. On approval the session switches to coding mode on the running log (a second log handle would not be seen by the agent's next step — the bug the test caught) and the plan's steps become the todo list.

5 · Reversible and parallel

flowchart LR T[task] --> W1[worktree 1 · model A] T --> W2[worktree 2 · model B] T --> W3[worktree 3 · model A] W1 --> J{project tests} W2 --> J W3 --> J J --> R[rank: verified > finished > has changes > smallest diff > fewest tokens] R --> M[squash-merge winner, discard others]

Every write is preceded by a checkpoint (file contents before the change). undo restores the newest steps and tells the model what was reverted. Best-of-N runs the same task in N worktrees and lets the project's own tests pick the winner; in evals, the hidden tests are never visible to candidates.

Pass rate went 55.6 → 69.4 → 61.1. Did the second half of phase 1 make things worse?

Not by itself. Tool and edit errors kept falling (25.8% → 3.6%, 40.6% → 7.0%). The four regressed tasks failed for model reasons: one session explained the fix and never edited, two ran out of steps, one wrote a wrong algorithm, and none touched the sandbox or the new tools. With 36 tasks, one task is 2.8 points; a ±3-task swing between runs of a weak model is noise. That is why the suite reports error rates and tokens next to the pass rate, and why runs are repeated.

Why did tokens go up?

More turns finish: the done gate turns a premature "done" into another round of edits, and fewer sessions die early from a poisoned history. Cost per solved task is the fair metric, and cached input is billed at a fraction of the price: 70–90% of input was cached once caching worked.

Fix mechanics before intelligence, measure every fix, and be ready to narrow a rule the numbers say is wrong.
