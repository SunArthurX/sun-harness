Settings planning and anti-drift

This milestone delivers a design, not the planned product features. We inspected existing runtime seams before selecting competitor features, then mapped every screenshot entry to an implementation task or an explained deferral.

What questions shaped the design?

Does a setting already exist? Is a feature native, browser-only or remote? Can configuration survive two writers? Can the exact review input be reconstructed? Which controls can the web renderer honestly expose? These questions led to revisioned settings, capability descriptors and durable input records.

Why a machine-readable plan?

A prose plan can omit a screenshot entry, invent a dependency or claim completion prematurely. The manifest checker rejects missing coverage, cycles, unknown acceptance IDs and completion without evidence. Its negative tests mutate a valid plan to show that those mistakes fail. It is also called by the normal Vitest suite.

Limits of the harness

File existence cannot prove correct behavior. Product tasks still need adversarial tests, restart and permission cases, bilingual UI checks and human evidence review. Smaller-model trials are specified but have not been run. A native adapter tested only with mocks is not a shipped computer-control feature.
