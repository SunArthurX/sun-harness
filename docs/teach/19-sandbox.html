19 · Safe by construction

Approval prompts protect nobody in full-auto, in evals, in bots, or after the hundredth prompt. The shell has to be safe even when nobody reads: a command may change the workspace, not the machine, and may not read your credentials.

One exec interface, three backends

flowchart LR B[bash tool] --> X[ExecSandbox.shell + env] J[background jobs] --> X V[verify gate] --> X N[best-of-N judge] --> X K[python kernel] --> X X --> SB[seatbelt · macOS] X --> BW[bubblewrap · Linux] X --> DK[docker · per session] X --> NO[none]

The sandbox turns a command into another command string: sandbox-exec -f profile.sb bash -c '…', bwrap --ro-bind / / … bash -c '…', or docker exec … bash -c '…'. Because it is just a string, the detached job wrapper can run it too: the wrapper (logging, exit code) stays outside, the command goes inside.

The seatbelt profile

(version 1)
(allow default)
(deny file-write*)
(allow file-write* (subpath "/workspace") (subpath "/repo/.git") (subpath "/private/tmp")
                   (subpath "/private/var/folders") (subpath "~/.npm") … (literal "/dev/null"))
(deny file-read-data (subpath "~/.ssh") (subpath "~/.aws") … (subpath "~/.sun"))
(allow file-read-data (subpath "~/.sun/skills") (subpath "~/.sun/plugins") …)
(deny network*)                       ; only when network is "off" or "allowlist"
(allow network* (remote unix-socket))
(allow network* (remote ip "localhost:*"))

Why deny reads of ~/.sun?

It holds the gateway token. A sandboxed command that can read gateway.json can ask the gateway to run anything outside the sandbox: an escape through the harness itself. The parts that are not secret (skills, plugins, notes, the agent workspace, worktrees) are re-allowed; in SBPL the last matching rule wins.

The best-of-N test failed after enabling the sandbox. Why?

npm test crashed with EPERM: lstat '/…/home'. Denying file-read* also denies metadata, and Node's module resolution calls realpath, which lstats every parent directory. The fix is file-read-data: contents stay hidden, directory listings and stats work.

Worktree commits failed inside the sandbox?

A worktree's .git is a file pointing to the main repository's .git/worktrees/<name>; commits write there. The sandbox adds git rev-parse --git-common-dir to the writable roots.

Did bubblewrap work on real Linux?

Not at first. Run in a Debian container, every command printed bash: /root/.bashrc: Permission denied. Denied files were hidden by bind-mounting /dev/null over them, but inside the new namespace a bound device node is not readable, and bash touches its rc file. Binding an empty regular file instead fixed it; the container then confirmed workspace writes, a read-only /root, a hidden ~/.ssh, a scrubbed secret, no outside network, and working loopback.

Network: off, on, or an allowlist

sequenceDiagram participant C as sandboxed curl participant P as sun proxy 127.0.0.1:random participant G as github.com participant E as evil.example C->>P: CONNECT github.com:443 P->>G: TCP P-->>C: 200 Connection Established C->>P: CONNECT evil.example:443 P-->>C: 403 not in sandbox.allow Note over C: direct connections are blocked by the OS profile (loopback only)

Two layers make the allowlist real on macOS and Linux: the OS profile allows only loopback, and the only thing listening there for the outside world is the proxy, which checks the host. Environment variables (HTTPS_PROXY, npm's proxy settings, NODE_USE_ENV_PROXY=1) make common tools use it. Inside Docker the allowlist relies on the proxy settings only, and the spec says so.

Secrets

Sandboxed commands lose the environment variables that carry the harness's own secrets: every *Env name in the config (provider keys, bot tokens) and credential-looking names (*_API_KEY, *_TOKEN, …). Shell rc files are unreadable too: they are where those keys were imported from.

Fewer prompts, not more

A command that cannot write outside the workspace is not worth an approval prompt in auto-edit. With sandbox.autoApprove on, sandboxed shell commands run without asking, the Codex "workspace-write" model. Phase 4 adds one exception: once web content is in the context, commands ask again.
